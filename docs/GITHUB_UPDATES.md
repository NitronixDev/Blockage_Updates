# GitHub releases and updates — 0.4

## Configure the application

In **Edit → Preferences**, enter a public GitHub repository as `owner/repository` or `https://github.com/owner/repository`. No repository is preconfigured. Startup checks are optional. **Help → Check for Updates** reads that repository's latest stable published release; drafts, prereleases and non-semantic tags are rejected. This release does not authenticate to private repositories.

For a release tagged `v0.4.1`, attach:

- `Blockage_0.4.1_Windows_x64.zip`, containing the portable `Blockage/` directory.
- `SHA256SUMS.json` with the filename mapped to its SHA-256 hash, as generated by the packaging command. GitHub's own `sha256:` asset digest is preferred when present.

The app downloads only a newer stable version, with a maximum 512 MiB archive. It verifies the announced length and SHA-256 before extraction. ZIP entry paths, types, checksums and expansion limits are checked. Package identity, version, main entry, required files and Windows executable signatures are checked before reporting success.

The update is extracted into a new directory below the user's Blockage data folder. The running installation is kept. After installation, **Open Folder** shows the result; **Save & Restart** saves changes and starts the downloaded Windows executable. Scene files remain at their own saved locations. Automatic installation/restart is a Windows feature; Linux was used to test the download and extraction service, not to launch the Windows binaries.

GitHub API rate limits, connection errors, missing artifacts and mismatched checksums produce a dialog and leave the running version available. The downloaded release is code from the configured repository, so use the repository that owns your Blockage distribution.

## Publish future versions

The included `.github/workflows/release.yml` runs on a `vX.Y.Z` tag in your repository. It checks that the tag matches `package.json`, installs the pinned dependencies, runs unit and syntax checks, prepares Windows Node/npm, creates the portable ZIP and SHA256SUMS file, and publishes them as GitHub release assets. The workflow uses `GITHUB_TOKEN` with release write permission; it is provided as source and has not been executed or published to a repository during this delivery.

1. Put the project source, lockfile, examples and `.github/workflows/release.yml` in your GitHub repository. Omit generated `release/`, local `runtime/` and `node_modules/` directories from git.
2. Set `package.json` and the root entries of `package-lock.json` to the same new stable version. Update the change notes, then commit the changes.
3. Push the matching `vX.Y.Z` tag. Allow GitHub Actions to run in that repository.
4. Once the release is published, clients configured to that repository can download it through Help → Check for Updates.

For a manual Windows build, prepare the portable `runtime/node` folder and run `npm ci`, `npm test`, `npm run check`, then `npm run release`. The packaging command refuses Linux executables. Output is `release/Blockage_X.Y.Z_Windows_x64.zip` and `release/SHA256SUMS.json`.

Maintainers can supply other prepared Windows runtime/dependency directories without replacing development dependencies:

```sh
node scripts/package-release.mjs --runtime path/to/runtime --dependencies path/to/node_modules --output path/to/release
```

Primary references: [GitHub releases API](https://docs.github.com/en/rest/releases/releases), [release assets and digest](https://docs.github.com/en/rest/releases/assets), [GitHub CLI release creation](https://cli.github.com/manual/gh_release_create), [checkout](https://github.com/actions/checkout) and [setup-node](https://github.com/actions/setup-node).
